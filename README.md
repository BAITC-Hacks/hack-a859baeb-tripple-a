# Org Agent — тестовый backend

Прототип для сопоставления организационных документов «до/после». FastAPI, SQLAlchemy, PostgreSQL; локальный запуск также поддерживает SQLite. Интерфейс тестирования — Swagger UI `/docs` с загрузкой файлов. Отдельный пользовательский frontend не реализован.

## Запуск с PostgreSQL

Из папки проекта, при запущенном Docker Desktop:

```sh
docker compose up --build
```

Откройте http://localhost:8000/docs. Проверка состояния: http://localhost:8000/health.
PostgreSQL хранит данные в именованном томе, оригиналы — в отдельном томе uploads. Порт базы наружу не открыт. Пароль в compose предназначен только для локального демонстрационного запуска.

## Запуск без Docker

Python 3.12 или 3.13:

```sh
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.lock
uvicorn app.main:app --host 127.0.0.1 --port 8000
```

По умолчанию используется `org_agent.db` (SQLite) и `data/uploads`. Для своей PostgreSQL перед запуском задайте `DATABASE_URL=postgresql+psycopg://USER:PASSWORD@HOST:5432/DATABASE`.

## Контрольная демонстрация

В другом терминале с активированным окружением:

```sh
python demo.py
```

Скрипт создаёт проект, загружает `examples/before.txt` и `examples/after.txt`, запускает сравнение и печатает JSON со ссылками на источники. Повторный запуск создаёт отдельный проект.

Ожидаемый результат:
- «Отдел снабжения» преобразован в «Департамент закупок» — явное указание в документе after.
- «Финансовый отдел» сохранён по совпадению названия.
- Возможная потеря функции «Ведёт реестр поставщиков».
- Возможное дублирование ежемесячного отчёта между двумя подразделениями.
- Возможный конфликт: закупки и независимый контроль закупок у одного подразделения.

Режим `demo` — детерминированные правила, не ИИ. Он ожидает строки `Подразделение: Название`, нумерованные функции и необязательные строки `Преобразование: Старое -> Новое`. Совпадение текста используется для демонстрации, похожие формулировки требуют проверки. Создание/ликвидация не выводятся из простого отсутствия названия. Для произвольных документов используйте режим `ollama`.

## Локальная языковая модель

Установите Ollama отдельно, загрузите подходящую для вашей машины модель, поддерживающую русский язык и структурированный JSON. Задайте её точное локальное имя:

```sh
export OLLAMA_MODEL='имя-установленной-модели'
export OLLAMA_URL='http://localhost:11434'
uvicorn app.main:app --host 127.0.0.1 --port 8000
```

В Docker Compose достаточно передать `OLLAMA_MODEL`; адрес Ollama настроен на хост. Сервис модели должен быть доступен из контейнера.

При создании анализа передайте `{"mode":"ollama"}`. Адаптер обращается к `/api/chat` с JSON Schema, `stream:false` и температурой 0. Модель получает текст и координаты фрагментов; все идентификаторы и цитаты проверяются сервером. Ошибка модели не подменяется результатом demo. Описание протокола: https://docs.ollama.com/api/chat.

MVP передаёт весь небольшой комплект в контекст: до 60 000 символов сериализованного запроса; запрос требует достаточного контекстного окна модели. pgvector пока не используется: для маленького контрольного набора отдельный этап векторного поиска не требуется. Следующий этап масштабирования — извлечение атомарных функций, embeddings и поиск кандидатов через pgvector перед проверкой моделью.

## API

1. `POST /projects` — `{"name":"Реорганизация"}`.
2. `POST /projects/{id}/documents` — multipart: `phase=before` или `after`, `file`.
3. `GET /projects/{id}/documents` — документы и предупреждения извлечения.
4. `GET /documents/{id}/fragments` — текст и координаты.
5. `POST /projects/{id}/analyses` — `{"mode":"demo"}` или `{"mode":"ollama"}`.
6. `GET /analyses/{id}` — сохранённое заключение.
7. `GET /projects/{id}/analyses` — история запусков.
8. `GET /documents/{id}/download` — оригинал.

Результат: `units`, `functions`, `changes`, `matches`, `findings`, `sources`, `summary`, `warnings`, `provenance`. Связь `evidence.fragment_id` ведёт к оригинальному тексту, названию документа, координатам и ссылке скачивания в `sources`. У каждого отклонения есть рекомендация и `requires_review=true`. В `matches` обязательна запись для каждой извлечённой исходной функции. Отрицательный вывод означает «не найдено в данном комплекте», а не доказанную фактическую утрату обязанности.

## Архитектура

Загрузка → извлечение текста с координатами → неизменяемые фрагменты → demo или модель → проверка структуры, ссылок, цитат и покрытия → сохранение снимка анализа.

- `app/parsers.py`: DOCX (абзацы и таблицы в порядке документа), текстовый PDF, XLSX, UTF-8 TXT.
- `app/db.py`: проекты, документы, фрагменты и анализы; внешние ключи для основных сущностей. Массивы результата хранятся JSON-снимком; ссылки внутри результата проверяются приложением, а не внешними ключами БД.
- `app/analysis.py`: правила демо, адаптер Ollama и валидация источников.
- `app/main.py`: HTTP API, сохранение оригиналов, ограничение размеров, история.
- Исходные файлы получают UUID-имена; SHA-256 используется для проверки происхождения и повторных загрузок.
- Схема создаётся через `create_all` для чистой базы. Для эволюции production-схемы необходимы миграции.

## Границы прототипа

- Нет OCR, распознавания графических оргструктур, старых `.doc/.xls`, колонтитулов и текстовых полей Word. DOCX ссылается на блок/строку таблицы, PDF — на страницу/строку извлечённого текста, XLSX — на лист/ячейку.
- Файл до 15 МБ, распакованный Office-файл до 60 МБ, документ до 250 000 символов. Комплект анализа до 150 000 символов/3000 фрагментов, до 500 функций. Для Ollama действует меньший лимит контекста.
- Синхронный анализ; нет очереди заданий, авторизации, многопользовательского разграничения доступа и антивирусной проверки. Запуск предназначен для локального тестирования на доверенных файлах, не для публичного сервера.
- Точная цитата не доказывает логическую обоснованность интерпретации. Извлечение может пропустить функцию; полнота покрытия проверяется только относительно извлечённых функций.
- Нет внешней нормативной проверки и бенчмаркинга. Нет автоматического утверждения рекомендаций.
- Реальная модель требует отдельного подключения и проверки на контрольном наборе. Тесты адаптера используют подмену ответа и не измеряют качество модели.

## Проверки

```sh
python -m pytest -q
```

Проверяются API-сценарий, три отклонения, реорганизация, сохранение, источники, история, повторная загрузка, изоляция комплектов проектов, неверные цитаты и фазы, неполное сопоставление, DOCX/PDF/XLSX, недоступность модели. Проверено: 18 автоматических тестов на SQLite, полный HTTP-сценарий с запущенным сервером, компиляция схемы PostgreSQL и валидность Docker Compose. Есть предупреждение библиотеки тестирования о будущем переходе с httpx на httpx2; проверки проходят. запуск контейнеров и интеграция с живой PostgreSQL/Ollama не проверялись (Docker daemon не запущен; запуск локальной PostgreSQL заблокирован ограничением shared memory).
